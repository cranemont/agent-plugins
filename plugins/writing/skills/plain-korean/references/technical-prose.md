# 한국어 기술 산문

기술 산문은 맥락을 모르는 독자도 결과와 근거를 다시 확인할 수 있게 쓴다. 저장소의 문서 템플릿과 문체가 이 지침보다 먼저다.

## 정보 구조

- 제목과 첫 부분에서 문서의 용도, 변경 결과, 결정 내용을 찾을 수 있게 한다.
- 한 문단에는 하나의 중심 내용을 두고, 다음 문장에는 근거·조건·영향을 이어 쓴다.
- 순서가 중요한 절차에는 번호 목록을 쓰고, 순서가 없는 병렬 정보에는 불릿을 쓴다.
- 표는 여러 대안이나 값을 같은 기준으로 비교할 때 쓴다. 짧은 서술을 표에 억지로 넣지 않는다.
- 긴 문서의 요약은 독자의 판단을 빠르게 할 때 남긴다. 본문을 그대로 반복하거나 새로운 주장을 요약에서 꺼내지 않는다.

## ADR

- 결정 제목에는 검토 주제보다 선택한 내용을 쓴다. `캐시 전략 검토`보다 `세션 캐시에 Redis를 사용한다`가 찾기 쉽다.
- 배경이 된 사실과 제약, 선택한 방안, 선택에 따른 장단점과 후속 영향을 구분한다.
- 대안을 나열했다면 채택하거나 제외한 이유도 남긴다. 근거가 없는 장점으로 결정을 미화하지 않는다.
- 사실, 가정, 결정, 미해결 사항을 섞지 않는다. 검증하지 않은 내용은 검증하지 않았다고 쓴다.
- 저장소가 정한 ADR 형식, 상태, 링크 규칙을 바꾸지 않는다.

## 구현 보고와 코드 리뷰

- 무엇이 바뀌었는지 먼저 쓰고, 판단에 필요한 이유와 영향을 잇는다.
- 변경 사항, 검증 결과, 남은 문제를 구분한다. 수행하지 않은 검증은 통과했다고 쓰지 않는다.
- 결함은 증상과 재현 조건을 먼저 쓰고, 확인한 원인과 추정 원인을 구별한다.
- 파일 경로, 함수명, 명령어, 버전, 수치, 재현 조건, 테스트 결과처럼 다시 확인할 수 있는 정보는 남긴다.
- 정확한 위치를 확인하지 않았다면 그럴듯한 경로나 줄 번호를 만들지 않는다.
- 마무리에는 독자의 판단이나 다음 작업에 필요한 제한 사항, 요청, 남은 일을 쓴다. 앞 내용을 그대로 반복하지 않는다.

## 커밋 메시지와 코드 주석

- 커밋 제목에는 변경의 대상과 동작을 쓴다. `버그 수정`, `기능 개선`처럼 내용이 없는 말만 쓰지 않는다.
- 저장소의 커밋 규약이 있으면 형식과 용어를 그대로 따른다.
- 주석은 코드가 이미 보여 주는 동작을 번역하지 말고, 코드만으로 알기 어려운 이유·제약·예외를 설명한다.
- 임시 제한이나 후속 작업을 적을 때는 조건과 추적할 이슈가 있으면 함께 남긴다.

## 고쳐 쓰기 예시

수정문에는 아래 맥락에 주어진 사실만 사용한다.

### 작업 보고

맥락: 저장 실패 메시지에 서버가 반환한 원인과 `다시 시도` 버튼을 추가했고 관련 테스트가 통과했다.

- 수정 전: `이번 작업을 통해 저장 실패 상황에서의 사용자 경험을 크게 개선할 수 있게 되었습니다. 관련 테스트도 성공적으로 수행했습니다.`
- 수정 후: 저장 실패 메시지에 서버가 반환한 원인과 `다시 시도` 버튼을 추가했다. 관련 테스트가 통과했다.

### 결함 보고

맥락: 패널은 1200×800으로 표시하고 저장된 파일은 1199×800이며, 반올림이 원인인지는 확인하지 않았다.

- 수정 전: `화면이 잘못된 값을 보여 주는 치명적인 문제가 확인되었습니다. 아마 반올림 문제인 것으로 보입니다.`
- 수정 후: `패널은 1200×800으로 표시하지만 저장한 파일은 1199×800이다. 반올림이 원인인지는 확인하지 않았다.`

### ADR

맥락: 세션 조회가 데이터베이스 읽기의 42%이고 Redis를 쓰면 운영 저장소와 캐시 무효화 작업이 늘어난다.

- 수정 전: `확장성을 극대화하기 위해 Redis를 도입하기로 결정했다.`
- 수정 후: `세션 조회가 데이터베이스 읽기의 42%를 차지해 Redis에 세션을 캐시한다. 운영할 저장소가 하나 늘고 캐시 무효화가 필요하다.`
