# 구현 맥락에 맞는 한국어

기능과 함께 생기는 UI 문구와 기술 산문을 읽기 쉽게 쓴다. 목표는 짧은 글이 아니라 독자가 필요한 내용을 찾고 이해한 뒤 판단하거나 행동할 수 있는 글이다. 군더더기와 직역투를 덜어도 동작 조건, 판단 근거, 제약은 남긴다.

## 작업에 맞는 지침 선택

- UI 문자열, i18n, 오류·상태 메시지를 작성하거나 고칠 때는 [UI 문구 지침](references/ui-copy.md)을 읽는다.
- ADR, README, 작업·결함 보고, 이슈·PR, 커밋 메시지, 코드 주석을 작성하거나 고칠 때는 [기술 산문 지침](references/technical-prose.md)을 읽는다.
- 두 종류가 함께 바뀌면 두 문서를 모두 읽는다.
- 규칙을 수정하거나 근거를 확인할 때만 [리서치 노트](references/research.md)를 읽는다.

## 먼저 확인할 것

- 작업 지시와 저장소 규칙을 읽는다. 제품의 문체, 용어집, 문서 템플릿이 있으면 그것이 먼저다.
- UI 문구는 한 문자열만 떼어 보지 말고 같은 화면의 앞뒤 상태, 인접 문구, 실제 동작을 확인한다.
- 문서는 누가 읽고 어떤 판단을 내려야 하는지 확인한다.
- 요청 범위를 문구 정제에서 UI 구조 변경이나 저장소 전체 문구 정비로 넓히지 않는다. 필요한 정보가 원문과 구현에 없으면 만들어 넣지 말고 빠진 정보를 알린다.

## 공통 원칙

### 의미와 동작을 보존한다

- 원문과 수정문에서 대상, 조건, 부정, 수치, 시점, 가능·권장·필수의 강도가 같은지 대조한다.
- 원문에 없는 원인, 수치, 사용자 감정, 검증 결과를 보태지 않는다.
- 제품의 실제 UI 라벨, 코드 식별자, 명령어, 파일 경로는 임의로 바꾸지 않는다.
- 문자열의 변수, 자리표시자, 마크업, 단축키 표기, 의도된 줄바꿈을 보존한다. 값에 따라 달라지는 문구와 문자열을 조합하는 곳도 함께 확인한다.

### 문장을 통째로 다시 본다

- 특정 단어나 조사를 검색해 일괄 치환하지 않는다. 정보의 순서와 문장 사이의 관계를 먼저 잡는다.
- 주제와 지시 대상이 앞 문장에서 자연스럽게 이어지는지 확인한다. 대상을 알 수 없는 대명사는 실제 이름으로 바꾼다.
- 영어의 명사 연쇄와 긴 수식어는 행위와 상태가 드러나도록 풀어 쓴다.
- 원문의 접속어를 그대로 옮기지 말고 실제 관계가 원인, 조건, 대조, 시간 순서 중 무엇인지 드러낸다.
- 피동, 복수 표지, 주어 생략은 원문의 형태가 아니라 한국어의 초점과 문맥에 맞게 정한다.
- `~에 대한`, `~를 통해`, `~것`, `-들`, 피동 표현은 금지어가 아니다. 해당 문장에서 뜻을 흐리거나 불필요할 때만 고친다.

### 필요한 정보부터 쓴다

- 서론, 예고, 자평보다 결과, 상태, 판단에 필요한 내용을 앞에 둔다.
- 없어도 판단이나 행동이 달라지지 않는 인사말, 반복, 추임새, 과한 비유를 덜어낸다.
- 원인, 조건, 예외, 복구 방법, 장단점은 단지 길다는 이유로 지우지 않는다.
- 같은 개념에는 같은 용어를 쓴다. 전문 독자에게 가장 정확한 말이라면 전문용어를 유지한다.
- 높임과 종결어미는 제품의 보이스톤과 저장소 관례를 따른다. 이 스킬이 해요체나 해라체를 일괄 지정하지 않는다.

## 검수

- 원문의 의미와 제품 동작을 바꾸거나 없는 사실을 보태지 않았는가?
- 독자에게 필요한 상태·근거·판단·다음 행동을 찾기 쉬운 순서로 놓았는가?
- 문장 사이의 대상과 논리 관계가 자연스럽게 이어지는가?
- 인접 문구나 문서와 용어·높임·서식이 맞는가?
- 가능하면 실제 화면이나 렌더링된 문서에서 읽고, 소리 내어 읽었을 때 걸리는 곳을 다시 고쳤는가?
