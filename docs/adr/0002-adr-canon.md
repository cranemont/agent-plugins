# ADR-0002: ADR 캐논 — 파생 상태, 순차 번호, 영문 파일명

`adr` 스킬이 모든 레포에 적용할 단일 캐논의 세 축을 확정한다. 실사용 레포 6곳의 규약 수렴·발산 조사와 웹 근거([research.md](../../skills/adr/references/research.md))를 바탕으로 했다.

## 맥락

여러 레포에서 ADR을 써 왔지만 번호 체계(순차 vs 날짜), status 필드(명시 vs 정책적 금지), 파일명 언어(한글 vs 영문)가 레포마다 갈라져 크로스레포 일관성이 없었다. 스킬 하나로 통일하려면 세 축을 먼저 확정해야 한다.

## 결정

| # | 결정 | 기각한 대안 |
|---|---|---|
| 1 | status 필드 금지 — 상태는 `superseded_by` 부재로 파생하고 인덱스에 자동 표시 | 명시적 status 라이프사이클 |
| 2 | `NNNN-` 4자리 순차 번호, 재사용 금지 | `YYYYMMDD-` 날짜 파일명 |
| 3 | 파일명 영문 kebab-case, 본문 한국어 | 한글 슬러그 |

## 기각한 대안

- **명시적 status 라이프사이클 (Proposed → Accepted → …)** — 웹 표준(AWS·MADR)이지만, "Accepted 후에도 status 줄은 고친다"는 예외가 불변성 원칙에 구멍을 낸다. status는 과거시제 기록에 새긴 현재시제 주장이고, 파생 가능한 데이터를 원본에 쓰면 드리프트한다. 솔로 워크플로우에선 Proposed 단계 자체가 불필요 — 논의 중인 것은 파일이 아니라 대화다.
- **날짜 파일명** — 시점이 파일명에 보이는 장점은 frontmatter `created`로 대체되고, 같은 날 여러 건의 접미사 문제와 긴 인용("20260803-adr05" vs "ADR-0012")이 남는다.
- **한글 슬러그** — 목록 가독성은 좋지만 BSD sed 문자클래스 오작동을 실제로 겪었고 URL 인코딩·크로스플랫폼 도구 호환이 나쁘다. 가독성은 인덱스의 한국어 제목 열이 담당한다.
- **레포별 선택 허용** — 마찰은 최소지만 "크로스레포 일관성"이라는 목표 자체를 포기하는 것.

## 결과

얻는 것: 어느 레포든 같은 규약, 스크립트 하나로 파싱·검증 가능한 frontmatter, "사후 수정" 실패 패턴의 원천 차단. 감수하는 것: 웹 표준 status 관행과 달라 외부 협업자에게 낯설 수 있고, 팀 리뷰 플로우(Proposed)가 없다.
