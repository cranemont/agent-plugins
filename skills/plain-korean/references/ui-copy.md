# 한국어 UI 문구

UI 문구는 사용자가 현재 상태와 다음에 할 수 있는 일을 이해하게 해야 한다. 화면 상태, 배치, 실제 동작을 확인한 뒤 고친다.

## 정보 순서

상황에 필요한 항목만 골라 다음 순서로 쓴다.

1. 현재 상태나 일어난 일
2. 사용자의 작업에 미치는 영향
3. 가능한 해결 방법이나 다음 행동

오류, 빈 화면, 로딩·지연, 오프라인, 권한 부족, 비활성 상태, 저장하지 않은 변경, 완료 알림에도 같은 기준을 적용한다. 모든 메시지에 세 항목을 억지로 넣지 않는다. 사용자가 이미 아는 정보나 할 수 없는 조치는 빼고, 중요한 복구 방법은 글자 수를 줄이려고 숨기지 않는다.

## 요소별 판단

- **작업 버튼:** 실행 결과가 드러나는 동사를 쓴다. 삭제를 실행하는 버튼이라면 `확인`보다 `프로젝트 삭제`가 분명하다.
- **탐색·선택 요소:** 이동할 곳이나 고를 대상을 나타내는 이름을 쓴다. 메뉴와 탭을 억지로 동사형으로 바꾸지 않는다.
- **닫기·고지 확인:** 실제 동작이 닫기나 확인뿐이면 `닫기`, `확인`을 써도 된다.
- **제목과 본문:** 제목은 현재 상태나 결정할 일을 알리고, 본문은 결과·조건·보충 설명을 맡는다. 같은 문장을 반복하지 않는다.
- **입력 안내:** 필드의 목적과 필요한 형식을 알려 준다. 자리표시자만으로 필드 이름을 대신하지 않는다.
- **오류:** 문제가 난 대상과 사용자가 할 수 있는 해결 방법을 구체적으로 쓴다. 원인을 모르면 추측하지 않고 사용자를 탓하지 않는다.
- **확인과 경고:** 대상과 실행 결과를 쓴다. 되돌릴 수 없는 동작이라면 구현에서 확인한 결과만 설명하고 버튼에도 실제 동작을 적는다.
- **진행과 완료:** 끝난 일과 남은 일을 구분한다. `정상적으로`, `성공적으로` 대신 저장·전송·반영된 대상을 쓴다.

짧은 영역에는 핵심 상태나 행동을 먼저 두고 상세 원인과 도움말은 보조 영역에 둔다. 정보 구조를 바꾸는 일이 요청 범위 밖이면 문구만 수정하고 필요한 구조 변경을 제안으로 남긴다.

## 동적 문구와 i18n

- 변수와 자리표시자를 삭제하거나 이름을 바꾸지 않는다. 개수, 날짜, 이름, 단위가 실제 값으로 들어간 완성 문장을 확인한다.
- 값의 받침 여부에 따라 조사가 깨질 수 있으면 조사를 피하도록 문장을 다시 쓰거나 저장소의 조사 처리 방식을 따른다.
- 문자열 조각을 이어 붙이면 어순과 조사가 깨지기 쉽다. 가능하면 번역 단위가 되는 완성 문장으로 구성하되, 구조 변경은 요청 범위 안에서만 한다.
- 복수형·선택 구문처럼 값에 따른 모든 변형을 확인한다. 사용하는 i18n 형식의 문법과 이스케이프를 보존한다.
- 같은 동작의 라벨은 화면마다 같은 용어를 쓴다.

## 접근성

- 보이는 라벨이 접근 가능한 이름에 포함되게 한다. 아이콘만 있는 버튼에는 동작을 설명하는 이름이 필요하다.
- 오류가 난 입력 항목과 고치는 방법을 색이나 아이콘만이 아니라 텍스트로도 알린다.
- 기술적으로 연결되지 않은 레이블이나 상태 알림을 발견하면 문구 정제와 구분해 구현 문제로 알린다.

## 고쳐 쓰기 예시

수정문에는 아래 맥락에 주어진 사실만 사용했다. 예시의 해요체는 제품 문체를 지정하지 않는다.

### 완료 메시지

맥락: 비밀번호 재설정 링크를 이메일로 보냈고 제품은 해요체를 쓴다.

- 수정 전: `비밀번호 재설정 링크가 성공적으로 이메일을 통해 전송되었습니다.`
- 수정 후: `이메일로 비밀번호 재설정 링크를 보냈어요.`

### 입력 오류

맥락: 생년월일 입력값은 `YYYY-MM-DD` 형식만 받는다.

- 수정 전: `입력된 생년월일의 형식이 유효하지 않습니다.`
- 수정 후: `생년월일을 YYYY-MM-DD 형식으로 입력해 주세요.`

### 삭제 확인

맥락: 프로젝트를 삭제하면 복구할 수 없다.

- 수정 전: `정말 삭제하시겠습니까? [확인] [취소]`
- 수정 후: `프로젝트를 삭제할까요? 삭제한 프로젝트는 복구할 수 없어요. [프로젝트 삭제] [취소]`
