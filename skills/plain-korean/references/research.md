# 한국어 UI·기술 문서 정제 원칙의 근거

이 문서는 `plain-korean` 스킬을 설계할 때 확인한 자료와 채택한 기준을 기록한다. 스킬을 적용할 때마다 읽을 필요는 없다. 웹 자료는 2026년 9월 3일에 확인했다.

## 조사 결론

아래 내용은 여러 출처를 바탕으로 이 스킬이 내린 설계 판단이다. 모든 출처가 각 항목을 직접 주장한다는 뜻은 아니다.

1. 쉬운 글은 단어 목록보다 독자, 목적, 사용 맥락에서 시작한다.
2. 간결함은 필요한 정보를 지우는 일이 아니다. 독자가 행동하거나 판단하는 데 필요한 조건과 결과는 남긴다.
3. UI 문구는 화면의 과업, 상태, 다음 행동과 함께 평가한다.
4. 기술 문서는 결론을 찾기 쉽고 근거와 제약을 다시 확인할 수 있어야 한다.
5. 문장 규칙은 문맥 판단을 돕는 진단 기준이어야 한다. 특정 조사나 어미를 전면 금지하면 의미와 자연스러움을 해칠 수 있다.

이 판단에 따라 표현 목록보다 의미 보존, 문맥 확인, UI와 기술 문서의 용도별 검수를 우선한다.

## 쉬운 한국어와 정보 구조

### ISO 24495-1:2023

[ISO 24495-1:2023 공식 안내](https://www.iso.org/standard/78907.html)와 [공개 미리보기](https://cdn.standards.iteh.ai/samples/78907/d194fac21d6a45f38bfcfec9657f7498/ISO-24495-1-2023.pdf)는 평이한 언어의 기준을 다음 네 가지로 잡는다.

- 독자가 필요한 내용을 얻는가
- 필요한 내용을 쉽게 찾는가
- 찾은 내용을 쉽게 이해하는가
- 그 정보를 쉽게 사용하는가

표준은 초안을 쓰기 전에 독자, 목적, 읽는 맥락을 파악하라고 권한다. 이 기준을 스킬의 공통 원칙과 검수 항목에 반영했다. “무조건 짧게”나 “특정 표현 금지”는 이 네 기준을 대신하지 못한다.

### 국립국어원

국립국어원의 [쉬운 공공언어 쓰기 길잡이](https://www.korean.go.kr/common/download.do?c_file_name=d1ce1113-cc07-4f4c-9ea2-dd920eecba7b.pdf&file_path=etcData&o_file_name=%E2%98%85%EC%89%AC%EC%9A%B4_%EA%B3%B5%EA%B3%B5%EC%96%B8%EC%96%B4_%EC%93%B0%EA%B8%B0_%EA%B8%B0%EB%B3%B8_%EA%B8%B8%EC%9E%A1%EC%9D%B4%28%EC%B5%9C%EC%A2%85_%EB%B0%B0%ED%8F%AC%29%ED%8E%BC%EC%B9%A8%EB%A9%B4.pdf) 17~19쪽은 문장의 목적과 전달 내용이 드러나야 하며, 문장 성분의 호응·생략·배열·과도한 연결을 살피라고 설명한다. 번역투와 명사 나열을 경계하면서도 핵심 판단 기준을 “문맥에 맞는 단어”에 둔다.

[2023년 국민의 글쓰기 능력 진단 체계 개발 보고서](https://www.korean.go.kr/common/download.do?c_file_name=54d339d1-7676-40c2-b029-2fbff757e1a0.pdf&file_path=reportData&o_file_name=2023%EB%85%84+%EA%B5%AD%EB%AF%BC%EC%9D%98+%EA%B8%80%EC%93%B0%EA%B8%B0+%EB%8A%A5%EB%A0%A5+%EC%A7%84%EB%8B%A8+%EC%B2%B4%EA%B3%84+%EA%B0%9C%EB%B0%9C%2820241015+%EC%B5%9C%EC%A2%85+%EC%88%98%EC%A0%95%EC%95%88%29.pdf)은 예상 독자와 설명 목적, 중심 내용, 뒷받침 정보의 적절성과 충분성, 전체 구성과 문단 구성을 함께 평가한다. 표현만 다듬고 정보 구조를 그대로 두는 감수로는 부족하다는 근거로 사용했다.

### 영한 번역투

김순영의 [「영한 번역에 나타난 번역투 문장」](https://www.korean.go.kr/nkview/nklife/2012_1/22_0105.pdf)은 번역투를 특정 단어 하나가 아니라 원문의 어휘·통사 구조·어순이 맥락 고려 없이 반복해서 옮겨진 결과로 설명한다. 73~78쪽의 사례는 영어의 소유 구문, 피동, 복수형, 전치사구를 한국어에 일대일로 대응할 때 문장이 어색해질 수 있음을 보여 준다. 동시에 번역투가 언제나 나쁜 것은 아니며 의도와 맥락을 따져야 한다고 밝힌다. 이 내용을 근거로 피동이나 `-들`을 금지하지 않고, 원문의 구조를 그대로 옮겼는지와 문장 전체의 초점을 확인하도록 했다.

## UI 문구

### 한국어 제품 문구

[앱인토스 UX 라이팅 가이드](https://developers-apps-in-toss.toss.im/design/ux-writing.html)는 제품 안에서 문체를 일관되게 쓰고, 능동형과 긍정형을 우선하며, 오류 상황별 문구와 버튼 라벨을 함께 다룬다. 해요체는 토스 제품의 보이스톤이므로 다른 제품에 일반화하지 않았다. 스킬은 저장소와 제품의 기존 문체를 먼저 따르도록 했다.

[Google Material 커뮤니케이션 원칙](https://codelabs.developers.google.com/codelabs/material-communication-guidance?hl=ko)은 UI 텍스트의 목표를 사용자 여정 지원으로 본다. 단어 선택, 길이, 스타일, 정보 계층을 사용자의 과업과 함께 판단하고, 실제 맥락에서 이해도와 작업 완료를 시험하라고 권한다. 이 때문에 문구를 파일 안의 독립된 문장으로만 보지 않고 화면 상태와 다음 행동을 확인하도록 했다.

### 오류, 버튼, 입력 안내

[Microsoft Windows 앱 작성 지침](https://learn.microsoft.com/en-us/windows/apps/design/style/writing-style)은 중요한 내용을 먼저 놓고, 필요한 정보는 희생하지 않으면서 군더더기를 줄이라고 권한다. 오류에는 사용자가 이해할 수 있는 상태와 실행 가능한 해결책을 제시하고, 버튼은 동작을 나타내며 대화상자의 질문에 답해야 한다고 설명한다.

[WCAG 2.2 오류 식별 기준](https://www.w3.org/TR/WCAG22/#error-identification)은 오류가 난 항목과 오류 내용을 텍스트로 알려야 한다고 정한다. [오류 수정 제안 해설](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)은 고치는 방법을 알 수 있을 때 사용자에게 제시하도록 한다. [레이블과 입력 안내 해설](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)은 입력 형식과 필수 조건을 포함한 안내가 오류를 예방한다고 설명한다. 이 근거를 UI 오류·입력 안내·접근성 항목에 반영했다.

## 기술 문서와 ADR

[Google 개발자 문서 보이스톤 지침](https://developers.google.com/style/tone)은 자연스럽고 직접적인 문체를 권하지만 구어체를 그대로 옮기거나 지나치게 재미를 추구하지 말라고 한다. 비유, 상투어, 불필요한 예고 문구, 장황하거나 끊기는 문장을 피하되 유용한 정보를 분명하게 전달하는 일을 우선한다.

[Google 접근 가능한 문서 지침](https://developers.google.com/style/accessibility)은 설명적인 제목, 제목 계층, 문단 첫 문장의 구별되는 정보, 병렬 목록을 통해 훑어보기 쉽게 쓰라고 권한다. 고정된 문장 길이는 영어 기준이라 스킬에 옮기지 않았고, 정보 구조 원칙만 채택했다.

[Microsoft 전문용어 지침](https://learn.microsoft.com/en-us/style-guide/word-choice/avoid-jargon)은 전문용어가 특정 독자에게는 정확하고 효율적인 약어가 될 수 있다고 본다. 일반 독자에게 익숙하지 않거나 더 쉬운 말로 같은 뜻을 전달할 때만 바꾸라고 한다. 따라서 기술 용어를 일괄 순화하지 않고 독자와 정확성을 기준으로 판단한다.

[GDS의 ADR 지침](https://gds-way.digital.cabinet-office.gov.uk/standards/architecture-decisions.html)은 나중에 합류한 사람도 결정 이유를 이해할 수 있도록 맥락을 보존하라고 한다. ADR을 결정 제목, 배경 사실, 결정, 긍정적·부정적 결과로 나눈다. 스킬은 특정 ADR 형식을 강제하지 않고 저장소 템플릿을 우선하되 이 정보가 빠지지 않았는지 확인한다.

## 설계 경계

- `~에 대한`, `~를 통해`, `~것`, `-들`, 피동을 문자열만 보고 지우지 않는다. 국립국어원 자료도 원문 구조의 무의식적인 일대일 대응과 문맥에 맞는 선택을 문제 삼는다.
- 쉼표 수와 문장 길이에 상한을 두지 않는다. 호응과 의미 단위가 흐려지는지를 본다.
- 표와 불릿의 사용 여부를 항목 수로 결정하지 않는다. 찾기와 비교가 쉬워지는지를 본다.
- 비유와 강조 표현의 허용 횟수를 세지 않는다. UI와 운영 문서에서는 대체로 직접 표현이 낫지만, 저장소의 문체와 전달 목적이 우선한다.
- “AI가 자주 쓰는 표현”을 탐지하거나 숨기는 일은 조사한 출처의 평이한 언어 기준과 무관하므로 목표에서 제외한다.
- 간결함을 이유로 파일 경로, 수치, 조건, 예외, 검증 결과, 장단점을 삭제하지 않는다.
